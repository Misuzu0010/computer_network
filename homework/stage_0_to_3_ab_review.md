# A. 概念辨析（17 / 20）

## A1：IP 与端口（2 / 2）

你的回答正确。这里应补充一点：端口不是“从什么端口发出的请求”，而是目标服务监听的目标端口；客户端自己的临时源端口也参与区分连接，但本题主要问服务器如何定位服务。

完整表达：

```text
IP 定位哪台主机，目标端口定位主机上的哪个网络服务。
```

## A2：TCP 与 UDP 可复用端口号（2 / 2）

正确。更严谨地说，操作系统通常按“传输层协议 + 本地地址 + 本地端口”管理监听端点，所以 TCP 7777 和 UDP 7777 可以同时存在。

## A3：通信角色（2 / 2）

正确。客户端和服务器首先是本次通信中的角色，不是程序一生不变的身份。一个程序可以作为客户端连接别的服务，同时作为服务器监听自己的端口。

## A4：端口不是 PID（2 / 2）

正确。你指出了 PID 与端口的区别，也知道一个进程可以使用多个端口。补充：多个连接还会通过源 IP、源端口、目标 IP、目标端口和协议共同区分。

## A5：访问 HTTPS 登录接口（1.5 / 2）

主线正确，但“TCP/TLS 建立字节流传输通道”不够精确：TCP 提供可靠字节流，TLS 在其上完成加密、完整性保护和服务器身份认证；HTTP 再定义登录请求和响应格式。

推荐顺序：

```text
DNS：域名 -> IP
IP/路由：把数据送到目标主机
端口：交给 443 上的服务
TCP：可靠、有序的传输
TLS：加密、完整性、证书身份认证
HTTP：规定请求、响应、Header、Body 和状态码
```

## A6：带宽与延迟（2 / 2）

正确。可以再补充：带宽像道路的容量，延迟像一辆车走完全程的时间；带宽高不代表距离近或 RTT 小。

## A7：逐层封装（2 / 2）

正确：

```text
应用数据 -> TCP/UDP 头部 -> IP 头部 -> 链路层头部
```

## A8：Ping 与网站访问（2 / 2）

正确。官网能访问说明至少有一条 HTTP/HTTPS 链路可用；Ping 使用 ICMP，服务器或中间设备可能过滤或限速 ICMP，因此 Ping 超时不能证明网站不可访问。

## A9：连接区分（0.5 / 2）

这是本部分最重要的误区。Token 和 Session 是应用层鉴权/会话信息，不是操作系统区分 TCP 连接的主要依据。

服务器通常根据下面的连接标识区分同时存在的连接：

```text
传输协议 + 源 IP + 源端口 + 目标 IP + 目标端口
```

同一台电脑上的三个程序通常使用不同的临时源端口，例如：

```text
启动器      192.168.1.8:51001 -> 服务器:443/TCP
游戏客户端  192.168.1.8:51002 -> 服务器:443/TCP
语音程序    192.168.1.8:51003 -> 服务器:443/TCP
```

即使三个程序使用同一个 Token，操作系统仍然能先按连接把字节交给正确的本地 Socket；服务器收到 HTTP 后，才进一步根据 Token/Session 判断“这是哪个账号”。

## A10：Socket 与 TCP（1 / 2）

结论正确，但理由太少。Socket 是程序使用网络通信的接口/端点，不等于 TCP。TCP Socket、UDP Socket 都存在；UDP 还可以使用无连接的 `sendto/recvfrom` 风格通信。

# B. 分层排错与工具选择（26 / 35）

## B1：169.254 地址（3 / 5）

你抓到了“没有正常网关、无法正常访问外部网络”的核心，但 `169.254.x.x` 更准确的含义是：系统没有从 DHCP 获得正常地址，于是自动配置了链路本地地址。它不等于“只能访问子网内所有设备”，连通能力仍需实际验证。

建议排查：

```text
确认网线/Wi-Fi
检查适配器状态
检查 DHCP 服务、路由器和默认网关
重新获取地址（由系统工具完成）
```

不应先修改 UE 登录代码，因为问题发生在应用层之前。

## B2：DNS、TCP、HTTP（5 / 5）

正确且简洁：DNS 已解析，TCP 已连接，HTTP 服务已经返回响应；`401` 优先检查 Token、登录状态、凭据和服务端鉴权规则，不是先查 DNS 或路由。

## B3：Connection refused 与 timeout（3.5 / 5）

“服务没有启用”正确；“被梯子拦截”不是本机 `127.0.0.1` 场景的首选解释，代理通常不会改变回环地址上是否有服务监听。

更可能的本机原因：

```text
服务未启动
服务监听了其他端口
服务只监听了其他地址族或地址
本地服务启动后立即崩溃并停止监听
```

`Connection refused` 通常表示目标主机可达，并且连接请求被立即拒绝，常见于目标端口没有监听；`timeout` 是在规定时间内没有得到连接完成或拒绝的响应，方向包括防火墙丢弃、路由问题、服务无响应等。

## B4：连接超时（2.5 / 5）

你知道 DNS 已成功，也知道超时不必然是服务端代码问题；但候选原因需要更贴近“连接阶段”，并且题目中的地址是 HTTP `9000`，不是 HTTPS。

至少可以写：

```text
客户端没有默认网关或路由异常
客户端到目标端口的防火墙/安全组丢弃数据
服务器没有响应 9000 端口，或端口映射错误
中间 NAT、代理或运营商链路丢弃连接
服务器过载，无法及时接受连接
```

下一步可以检查：`ipconfig`、到 IP 的 `tracert`、服务器端口监听、防火墙规则，以及从另一台网络不同的机器测试。不能仅凭超时断定业务代码崩溃，因为请求可能还没有到达 HTTP 进程。

## B5：tracert 星号（4 / 5）

结论基本正确。更严谨的说法是：星号只表示该跳没有按探测方式返回 ICMP 响应，可能是过滤、限速或设备策略；由于第 12 跳仍到达目标，不能据此说链路在第 6 跳中断。

不要说“绕过了不回应 Ping 的节点”作为确定事实；`tracert` 只是继续使用更大的 TTL 发送探测，真实业务数据是否经过该节点仍由路由决定。

## B6：工具选择（3 / 5）

你的答案顺序不清楚，且遗漏了 `curl` 的独立用途。建议明确写成：

| 任务 | 首要工具 |
|---|---|
| 查看登录 JSON 和 Authorization Header | Burp Suite |
| 确认域名解析到哪个 IP | nslookup |
| 观察 TCP 是否重传 | Wireshark |
| 检查 HTTP 状态码和响应头 | curl（或 Burp Suite） |

记忆方法：

```text

DNS -> nslookup
TCP/UDP 包和重传 -> Wireshark
路径 -> tracert
```

## B7：Ping 好但游戏卡（5 / 5）

你列出的丢包、抖动、带宽和重传都属于合理候选；“Ping 只能说明 ICMP 能回应”也正确。

缺少的是“每个候选如何验证”。可以建立下面的对应表：

| 候选问题 | 观察证据 |
|---|---|
| 抖动 | 连续 RTT 的最大值、最小值、标准差或时间序列 |
| 丢包 | Wireshark、游戏网络统计中的丢包率和连续丢包段 |
| TCP 重传 | Wireshark 中的 retransmission、duplicate ACK |
| UDP 乱序 | 游戏包序号跳变、迟到包数量 |
| 带宽不足 | 上下行吞吐、发送队列、服务器出口带宽 |
| 服务器卡顿 | 服务器帧时间、Tick 时间、网络线程队列 |
| 客户端性能问题 | FPS、Frame Time、CPU/GPU、特效加载时间 |
| 插值/同步频率问题 | 状态更新频率、插值缓冲、远端角色位置误差 |

`ping 25ms` 只验证了 ICMP 往返的一部分情况，不能证明游戏 UDP/TCP 数据、服务器 Tick 或客户端渲染都正常。

# 本次最需要补强的知识

## 1. 连接标识与应用身份是两层问题

```text
Socket/四元组：操作系统和传输层用来区分“哪条连接”
Token/Session：应用层用来判断“哪个用户、是否有权限”
```

先按 Socket 把字节交给正确程序，再由 HTTP/游戏协议解析 Token 和业务数据。

## 2. 故障题必须写“候选原因 -> 证据”

不要只写：

```text
可能是丢包、抖动、带宽低。
```

改写为：

```text
候选：抖动
证据：连续 RTT 波动、位置包到达间隔变化
工具：ping 时间序列、Wireshark、UE 网络统计
```

## 3. `refused`、`timeout` 和 `401` 所处阶段不同

```text
refused：连接阶段立即被拒绝，常见是没有监听
timeout：连接阶段没有及时得到响应，可能尚未到达服务
401：已经到达 HTTP/应用层，但鉴权没有通过
```

这是排错时非常有价值的阶段定位线索。
