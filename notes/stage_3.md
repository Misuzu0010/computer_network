# Stage 3：TCP、UDP 与实时网络基础

## 一、本次练习结论

### 已经掌握

- 高频角色位置丢失旧更新后，通常直接使用更新的位置，不等待过时位置重传。
- TCP 一次读取不等于一次应用层消息；一次读取可能得到半条、一条或多条消息。
- 购买物品需要可靠处理和服务器权威；枪口火焰等短暂表现允许偶尔丢失。
- 技能的能量、冷却、范围检测和伤害应由服务器执行或裁决；客户端负责即时表现。
- 网络选型要根据数据丢失、迟到、乱序后的后果判断，而不是简单背诵“TCP 慢、UDP 快”。

### 暴露出的主要问题

1. 不知道位置包需要哪些字段。解决办法不是猜 UE 固定字段，而是根据需求设计协议字段。
2. 把时间戳当成判断新旧数据的唯一方案。时间戳可用，但跨机器时钟可能不一致；递增序号更适合判断乱序和过时包。
3. 把 UDP 的“无连接”理解得过于绝对。UDP 本身不维护 TCP 式连接，但游戏仍然需要登录、心跳、超时和断线状态。
4. 把 UDP 的能力表述为“只管完整性”。UDP 只提供数据报和基本校验，不保证送达、顺序、去重或及时到达。
5. 对开火命中的职责边界还不够清楚。客户端可以预测表现，但最终命中、伤害和弹药必须由服务器决定。
6. 对技能特效卡顿的原因过早归结为“返回特效请求太多”。还要区分网络抖动、可靠消息堆积、服务器处理延迟、同步频率和本地特效加载卡顿。

## 二、必须建立的核心模型

### 1. 状态与事件

状态描述“现在是什么”：

```text
HP = 80
位置 = (100, 200, 300)
弹药 = 12
```

状态通常可以由后续更新覆盖。旧位置或旧朝向过时后，可以直接丢弃。

事件描述“发生了一次什么事”：

```text
购买物品、拾取物品、比赛开始、死亡、确认施法
```

事件不能简单依靠下一条事件覆盖，通常需要可靠处理、响应和去重。

判断口诀：

```text
丢了以后，新状态能覆盖它吗？
迟到了以后，它还有价值吗？
```

### 2. 序号、Tick 与时间戳

位置包可以这样设计：

```cpp
struct FMovementPacket
{
    uint32 SequenceNumber; // 发送方递增的更新序号
    uint32 ServerTick;     // 服务器逻辑帧编号
    double Timestamp;      // 用于插值或延迟估算的时间信息
    FVector Position;      // 玩家位置
};
```

- `SequenceNumber`：判断新旧、丢包和乱序，最直接。
- `ServerTick`：判断状态属于哪一个服务器逻辑帧。
- `Timestamp`：用于插值和延迟计算，但不要盲信不同机器的本地时钟。

接收方保存最新序号：

```text
收到序号 103 → 接受
随后收到序号 102 → 丢弃，因为已经过时
```

如果序号有固定宽度并可能溢出，需要使用序号环比较；初学阶段先理解“递增序号判断新旧”即可。

## 三、TCP 可靠性与消息边界

TCP 提供的是可靠、有序的字节流，依靠：

- 序号：标记字节位置。
- 确认号：告诉发送方已连续收到哪里。
- 校验：发现数据损坏。
- 重传：补发丢失或损坏的数据。
- 流量控制：避免接收方缓冲区被撑爆。
- 拥塞控制：网络拥塞时降低发送速度。

TCP 不保留应用层消息边界：

```text
两次 send 不保证两次 recv
一次 recv 可能拿到半条、一条或多条消息
```

自定义 TCP 服务必须使用消息 framing，常见方法：

- 固定长度：每条消息大小相同。
- 长度前缀：`[长度][正文]`，最常用的二进制方案之一。
- 分隔符：例如文本协议使用 `\\n`。
- 自描述头：长度、版本、类型、请求 ID、正文。

长度前缀解析流程：

```text
收到数据 → 追加到接收缓冲区
→ 长度字段不完整：等待
→ 正文不完整：等待
→ 正文完整：取出并处理
→ 缓冲区还有数据：继续循环解析
```

必须限制长度字段，例如超过 `MaxMessageLength` 时断开或拒绝，不能让客户端决定任意内存分配。

## 四、UDP 的正确理解

UDP 的特点：

- 无 TCP 式握手和连接状态。
- 每次发送是独立数据报，并保留数据报边界。
- 不保证送达、顺序、去重或及时到达。
- 提供基本校验，但不是可靠传输。

UDP 无连接不等于游戏无连接。UE 或游戏协议仍然要处理：

```text
加入服务器、身份验证、心跳、超时、断线、重连、状态恢复
```

如果需要，应用层可以在 UDP 上增加：

```text
序号、ACK、超时重传、去重、排序、请求 ID
```

因此：

```text
Reliable 不等于 TCP
UDP 也可以承载可靠消息
```

## 五、UE 多人技能的职责模板

```text
客户端输入
→ 本地立即播放预测表现
→ 发送一次技能或开火请求
→ 服务器验证玩家状态和请求参数
→ 服务器扣能量、开始冷却、检测范围、计算伤害
→ 服务器同步 HP、能量、冷却等权威状态
→ 相关客户端本地播放已确认的特效
```

客户端可以预测：

- 起手动画。
- 枪口火焰。
- 后坐力。
- UI 中暂时的冷却表现。

服务器必须裁决：

- 是否允许释放。
- 是否有足够能量。
- 冷却是否结束。
- 是否命中。
- 伤害是多少。
- 弹药、HP、背包和货币最终是多少。

不要把特效的每一帧通过网络发送。服务器通常只通知“一次技能事件”，客户端本地完成动画和粒子播放。

## 六、协议选型表

| 数据 | 常见方案 | 主要理由 |
|---|---|---|
| 登录 | HTTPS | 可靠且需要 TLS 加密 |
| 聊天 | TCP / WebSocket | 消息需要可靠、有序 |
| 高频位置 | UDP 或 UE 实时网络层 | 旧位置可丢弃，避免等待过时数据 |
| 购买物品 | HTTPS/TCP 或可靠游戏消息 | 需要服务器确认、去重和一致结果 |
| 语音 | UDP 或基于 UDP 的实时方案 | 旧语音迟到后价值很低 |
| 补丁下载 | HTTPS/TCP | 文件必须完整 |

选型时不要只按功能名称判断。同一个“开火功能”中，本地特效、开火请求、伤害结果和弹药状态可以采用不同策略。

## 七、网络异常的定位方法

看到“本地立即播放，服务器半秒后扣能量，其他人特效卡顿”，按链路拆分：

```text
客户端发送是否及时？
请求是否丢失或重传？
服务器是否及时处理？
服务器是否被大量可靠消息堵住？
权威状态多久复制一次？
远端事件到达是否抖动？
本地特效是否首次加载或渲染卡顿？
```

现象和初步方向：

| 现象 | 优先怀疑 |
|---|---|
| 固定晚半秒但播放流畅 | 服务器处理、RPC 排队或复制频率 |
| 其他移动和特效都一顿一顿 | 抖动、丢包、服务器卡顿 |
| 多个特效突然一起出现 | 消息堆积后集中处理 |
| 只有第一次特效卡 | 资源加载、Shader 编译或本地性能 |
| 本地先成功后又被取消 | 客户端预测被服务器拒绝并校正 |

不要一看到卡顿就断定是“UDP 不够快”或“返回特效帧太多”。先确认数据是在网络、服务器、复制还是渲染阶段变慢。
