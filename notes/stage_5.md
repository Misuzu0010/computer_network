# Stage 5：游戏网络设计的通用原则

## 一、阶段定位

Stage 5 是进入 UE 网络框架前的设计过渡层。目标不是马上记住某个 RPC API，而是能够先回答：

```text
客户端负责什么？
服务器裁决什么？
哪些数据需要同步？
数据是状态还是事件？
丢包、迟到、重复后怎么办？
谁有资格请求某个网络实体？
断线和重连如何恢复？
```

本阶段采用一个小型网络同步纵切项目作为练习载体：

```text
两名玩家
一个小场景
一个简单敌人
玩家移动、攻击、受击、死亡和重生
服务器判定命中与伤害
```

这个纵切项目先独立验证网络基础设施，成熟后再把通用部分迁移到主 ARPG 项目。主项目中的 Boss AI、多小怪同屏、复杂攻击判定和性能优化不在本阶段一次性网络化。

---

## 二、客户端不可信与服务端权威

核心原则：

> 客户端提交输入和意图，服务器验证请求、计算结果并维护权威状态。

客户端可以提交：

```text
移动方向
攻击输入
瞄准方向
技能编号
交互目标
输入序号
```

客户端不应直接提交并要求服务器相信：

```text
我造成了 999999 点伤害
我已经命中目标
我获得了传奇装备
我的金币变成了 1000000
我现在位于任意坐标
```

典型开火链路：

```text
客户端按键
→ 本地立即播放开火表现
→ 发送开火请求
→ 服务器检查玩家、武器、弹药、冷却和射速
→ 服务器执行命中检测
→ 服务器计算伤害并修改 HP、Ammo
→ 同步权威结果
→ 各客户端表现结果
```

服务端权威不等于所有计算都必须放到服务器。客户端可以负责 UI、动画、音效、粒子、摄像机和预测表现，但这些计算不能直接成为全体玩家共享的最终事实。

### 服务器验证的三类内容

身份与权限：

```text
请求是否来自对应玩家？
玩家是否拥有这个角色和武器？
```

状态：

```text
玩家是否存活？
是否在冷却？
资源是否足够？
是否处于眩晕、翻滚等禁止状态？
```

参数：

```text
方向是否合法？
距离是否超限？
攻击频率是否异常？
输入序号是否合理？
```

## 三、输入、权威状态和表现事件

一个多人 Gameplay 功能至少拆成三层：

### 1. 输入

```text
玩家按下技能键
玩家朝某个方向瞄准
玩家尝试拾取某个物品
```

由客户端产生并发送请求。

### 2. 权威状态

```text
HP
Ammo
Energy
CooldownEndTime
bIsDead
CurrentWeapon
Inventory
BossPhase
```

由服务器修改并同步。

### 3. 表现事件

```text
播放爆炸特效
播放受击音效
显示一次伤害数字
播放死亡动画
```

通常由服务器确认结果后触发，各客户端在本地播放完整表现。

一个技能可以表示为：

```text
输入：ActivateSkill
状态：Energy、CooldownEndTime
结果：命中目标、伤害、目标 HP
表现：动画、特效、音效
```

不要把特效的每一帧通过网络发送。服务器只需通知一次技能事件，客户端完成本地渲染。

## 四、状态同步与事件同步

### 4.1 状态

状态描述“现在是什么”：

```text
HP = 80
Ammo = 12
位置 = (100, 200, 300)
bIsDead = false
```

状态通常可以被后续值覆盖。漏掉 `HP=80`，但收到 `HP=60`，仍可以恢复当前结果。状态适合：

```text
初始同步
增量同步
新值覆盖旧值
晚加入恢复
断线重连快照
```

### 4.2 事件

事件描述“一次发生了什么”：

```text
玩家死亡
玩家拾取物品
比赛开始
购买完成
技能释放成功
播放爆炸
```

事件丢失后，后面可能没有机会重新说明，因此需要考虑可靠传递、事件 ID、状态补偿或日志记录。

### 4.3 状态和事件通常组合使用

死亡既是状态又有事件：

```text
状态：bIsDead = true、HP = 0、RespawnTime
事件：播放死亡动画、更新击杀提示、播放音效
```

事件丢失时，客户端仍可通过状态修正；状态保证最终一致，事件负责即时表现。

### 4.4 常见分类

| 内容 | 主要类型 |
|---|---|
| 当前 HP | 状态 |
| 受到一次伤害 | 事件/过程 |
| 当前是否死亡 | 状态 |
| 死亡瞬间 | 事件 |
| 当前金币 | 状态 |
| 购买操作 | 事件 |
| 购买后的余额 | 状态 |
| 当前坐标 | 状态 |
| 播放爆炸 | 表现事件 |

## 五、高频、低频、可靠和不可靠

可靠性与同步频率是两个不同维度：

```text
高频 + 不可靠：常见于位置、朝向
低频 + 可靠：常见于 HP、死亡、装备
高频 + 可靠：容易堆积，通常危险
```

### 5.1 高频状态

典型数据：

```text
位置、速度、旋转、瞄准方向、部分物理状态
```

特点：

```text
变化快
旧数据很快过时
新状态可以覆盖旧状态
```

常用策略：

```text
携带序号或 Server Tick
丢弃迟到旧状态
允许偶尔丢失
插值显示
必要时服务器校正
```

### 5.2 低频状态

典型数据：

```text
当前武器、队伍、Ready、是否死亡、比赛阶段、Boss 阶段
```

特点：

```text
变化少
Gameplay 影响大
晚加入和重连仍需要
```

通常采用服务器权威、变化时同步、初始同步和状态快照。

### 5.3 Reliable 与 Unreliable

Reliable 通常表示框架会尽力保证消息按要求处理，可能重传、去重和维持相关顺序；它不代表业务一定成功，也不代表断电后还能送达。

Unreliable 表示消息可以丢失、乱序或被丢弃，不会为了每条历史消息无限重传。它不代表消息一定会丢，也不代表没有序号。

### 5.4 为什么不能高频 Reliable

如果每秒发送 60 次可靠位置：

```text
位置20丢失
→ 重传位置20
→ 后续位置堆积或等待
→ 带宽和队列增长
→ 延迟升高
→ 旧状态集中到达
```

高频状态通常让新值覆盖旧值，而不是可靠重传所有历史值。

### 5.5 项目初版分类

| 数据 | 类型 | 可靠性方向 |
|---|---|---|
| 玩家位置 | 高频状态 | 不可靠或可覆盖更新 |
| 玩家朝向 | 高频状态 | 不可靠或降低频率 |
| HP | 权威状态 | 可靠同步 |
| Ammo | 权威状态 | 可靠同步 |
| Energy | 权威状态 | 可靠同步 |
| Cooldown | 权威状态 | 可靠同步 |
| 枪口火焰 | 表现事件 | 可不可靠或本地播放 |
| 爆炸特效 | 表现事件 | 可不可靠 |
| 比赛开始 | 关键事件/状态 | 可靠 |
| 背包变化 | 权威状态 | 可靠、可恢复 |
| 心跳 | 控制消息 | 单次丢失通常可接受 |

判断口诀：

```text
丢了以后，新状态能覆盖它吗？
迟到了以后，它还有价值吗？
能否从服务器重新恢复？
是否影响共享规则或玩家资产？
```

## 六、Ownership：网络实体的所有权

Ownership 主要回答：

> 哪个连接有资格对某个网络实体发起控制请求？

它不等于：

```text
服务器权威
对象只存在于某个客户端
客户端可以随意修改对象
```

简单关系：

```text
客户端连接 A
→ PlayerController_A
→ Character_A
→ Weapon_A
```

玩家 A 可以请求控制自己的角色和武器，但服务器仍检查：

```text
是否存活
是否装备该武器
是否有弹药
是否在冷却
参数是否合法
```

口诀：

```text
Ownership：谁能请求
Authority：谁能决定
```

### 6.1 公共世界物体

宝箱、地面物品和公共机关通常由服务器管理。客户端只能请求：

```text
我想与 Chest_01 交互
```

服务器检查距离、物品状态、竞争关系和玩家条件后，决定最终结果。

### 6.2 不同的“归属”不能混用

以下概念可能不同：

```text
网络所有权：哪个连接有资格请求
控制关系：哪个 Controller 控制 Pawn
阵营归属：红队还是蓝队
资产归属：物品属于哪个账号
攻击来源：谁发起了伤害
```

不要用一个 Owner 字段表达所有业务关系。

### 6.3 谁需要看到数据

拥有者不等于唯一接收者：

```text
自己的背包：只发给拥有者
角色位置：发给相关玩家
比赛开始：可能发给所有人
```

不应发送给客户端的数据，不能只依赖 UI 隐藏；客户端已经收到的数据可能被作弊程序读取。

## 七、可预测逻辑和服务器裁决

客户端可以立即预测：

```text
攻击起手动画
枪口火焰
后坐力
摄像机震动
技能起手动作
本地 UI 反馈
```

服务器必须裁决：

```text
是否允许攻击/施法
最终位置
是否命中
伤害数值
弹药、HP、能量
死亡、重生
掉落、背包、比分
Boss 阶段转换
```

判断方法：

```text
预测错误只影响本地画面？可以考虑预测。
预测错误会影响其他玩家或不可逆状态？必须等服务器裁决。
```

预测流程：

```text
客户端立即表现
→ 发送请求
→ 服务器确认或拒绝
→ 客户端保持、取消或校正预测
```

预测表现可以错，权威状态不能靠猜。

## 八、心跳、超时、断线和重连

### 8.1 心跳

心跳用于确认最近仍可通信、测量 RTT、维持部分 NAT 映射。它不是 Gameplay 业务消息，不负责伤害、扣款或奖励。

如果玩家近期持续发送有效游戏数据，这些数据本身也能证明连接活跃，不必每帧额外发送心跳。

单次心跳丢失通常不需要可靠重传，因为下一次心跳或普通业务数据可以证明连接仍然可用。

### 8.2 超时

不能一丢心跳就踢人。可以使用状态：

```text
Connected
→ Suspected
→ TimedOut
→ Disconnected
```

超时时间需要考虑 RTT、抖动、丢包、心跳间隔和保留状态的成本。阈值太短会误判，太长会释放资源过慢。

### 8.3 断线处理

服务器可选择：

```text
立即移除
暂时保留角色
AI 接管
```

这属于 Gameplay 设计，需要明确断线期间是否能被击杀、是否能被拾取、重连后是否恢复控制。

### 8.4 重连

重连不是简单重新建立 Socket：

```text
建立网络连接
→ 身份验证
→ 恢复房间/比赛
→ 获取当前状态快照
→ 补发必要结果
→ 恢复实时同步
```

不要只依赖 IP 判断原玩家。应使用账号 ID、Session ID、重连 Token、房间 ID 等经过服务器验证的标识。

重连依据服务器状态恢复：

```text
当前 HP、位置、武器、冷却、死亡状态、敌人 HP、Boss 阶段
```

不应重播断线期间全部历史移动和特效。

### 8.5 重连状态机

```text
Connected
→ Suspected
→ Disconnected
→ Reconnecting
→ RecoveringState
→ Connected
```

服务器仍是权威方，客户端不能用本地记忆覆盖服务器保存的状态。

## 九、带宽预算和同步频率

粗略估算公式：

```text
每秒数据量
≈ 单条消息大小 × 每秒发送次数 × 接收人数
```

例如位置状态 40 字节、20 Hz、4 个玩家、每个客户端看到其他 3 人：

```text
40 × 20 × 3 × 4
= 9600 字节/秒
≈ 9.4 KB/s
```

实际还要加上协议头、Actor 标识、RPC、属性、确认、加密和其他流量。

同步频率不等于渲染帧率：

```text
客户端渲染 60 FPS
网络状态 20 Hz
客户端通过插值补足中间画面
```

常见降低成本的方法：

```text
降低远处对象频率
只在变化时发送
压缩数据
只发给相关客户端
使用插值和预测
合并小消息但避免增加过多等待
```

不能默认所有对象都发给所有客户端。多小怪同屏时，需要逐渐引入相关性、优先级和休眠等策略。

## 十、项目化网络方案：小型 ARPG 纵切

### 10.1 项目范围

```text
两名玩家
一个小场景
一个简单敌人
玩家移动、攻击、受击、死亡、重生
服务器判定命中和伤害
```

暂时不做：

```text
自定义可靠 UDP
自定义移动预测
复杂服务器回溯
大量小怪同步优化
完整 Boss 阶段
复杂技能树
商城和账号系统
```

### 10.2 网络职责表

| 功能 | 客户端输入 | 服务器验证/计算 | 权威状态 | 客户端表现 |
|---|---|---|---|---|
| 移动 | 输入方向 | 速度、状态、位置 | 位置、速度 | 本地响应、远端插值 |
| 攻击 | 攻击请求 | 冷却、弹药、命中、伤害 | Ammo、HP | 动画、音效、特效 |
| 敌人受击 | 不提交最终伤害 | 服务器命中 | EnemyHP | 受击动画 |
| 敌人死亡 | 不直接决定 | HP 到 0 的状态转换 | bIsDead | 死亡特效 |
| 玩家死亡 | 不直接决定 | HP 到 0 的状态转换 | bIsDead | 死亡界面 |
| 玩家重生 | 请求或等待 | 重生时间和位置 | HP、位置、状态 | 重生表现 |
| 断线重连 | 重连请求 | 身份和房间验证 | 当前完整快照 | 恢复控制 |

### 10.3 第一版数据结构示例

```cpp
struct FPlayerMovementState
{
    uint32 SequenceNumber; // 移动更新序号
    uint32 ServerTick;     // 服务器逻辑帧编号
    FVector Position;      // 服务器认可的位置
    FVector Velocity;      // 服务器认可的速度
    uint8 MovementMode;    // 移动模式
};

struct FCombatState
{
    int32 CurrentHP;        // 当前生命值
    int32 MaxHP;            // 最大生命值
    int32 CurrentAmmo;      // 当前弹药
    bool bIsDead;           // 是否死亡
    bool bCanAttack;        // 当前是否允许攻击
    float CooldownEndTime;  // 冷却结束时间
};

struct FAttackRequest
{
    uint32 InputSequence;  // 客户端输入序号
    FVector AimDirection;  // 客户端提交的瞄准方向
    uint32 ClientTick;     // 客户端逻辑帧编号
};
```

实际 UE 移动同步优先使用 `CharacterMovementComponent` 已有能力，不在第一版重新实现完整移动协议。

### 10.4 项目带宽估算

假设：

```text
2 名玩家
1 个敌人
位置状态约 40 字节
20 次/秒
```

仅位置正文大约：

```text
玩家位置：40 × 20 × 2 × 2 = 3200 字节/秒
敌人位置：40 × 20 × 2 = 1600 字节/秒
合计约 4.7 KB/s
```

这是数量级估算，不包含协议和其他 Gameplay 数据。

## 十一、功能设计的十个问题

设计任意多人功能时，先回答：

```text
1. 客户端提交的是什么输入？
2. 哪些数据不能由客户端直接决定？
3. 服务器验证哪些条件？
4. 服务器修改哪些权威状态？
5. 哪些表现可以本地立即执行？
6. 哪些内容是状态，哪些是事件？
7. 数据频率是多少？
8. 丢失或迟到后怎么处理？
9. 谁需要收到这些数据？
10. 晚加入和重连如何恢复？
```

如果这些问题还答不出来，不要先开始写 RPC。
